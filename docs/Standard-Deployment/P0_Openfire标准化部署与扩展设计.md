# Openfire 标准化部署与扩展设计

> 版本：v1.4 · 2026-09-21 · 状态：**定稿（v1 首版）**
> 读者：Openfire 测试/部署负责人 + 协作平台架构负责人
> 定位：本文是「Openfire 标准化部署与扩展」的**详细设计**，也是未来要开发的「部署管理平台」的**需求依据**。

---

## 一、文档目的

把「现在这套 Openfire 部署」从「手工搭出来的固定环境」，升级成一套**标准化的、可按规模扩展的、可图形化操作**的部署体系，最终落地为一个**部署管理平台（图形化 Web 控制台）**。

一句话目标：**不同规模、不同环境，图形化界面完成部署 / 扩展 / 回退 / 备份，高可用自动容灾不中断，数据自动备份本地 + 异地。**

> **核心红线（贯穿全文）**：最终交付的部署管理平台必须是**完全可视化**的——所有操作（部署 / 扩展 / 回退 / 备份 / 恢复 / 监控）都在图形界面点选完成，**一键处理，使用者全程不写任何命令、不碰任何代码**。底层的 Docker 命令、SQL、脚本由平台自动执行，对使用者完全透明。

## 二、需求定义（要做什么）

### 2.1 四大核心能力（四个「一键」）

| 能力 | 含义（大白话） | 典型场景 |
|------|--------------|---------|
| **一键部署** | 界面点一下，从零搭起一套可用的 Openfire 服务 | 新环境/新客户，10 分钟上线 |
| **一键扩展** | 界面点一下，从 1 个实例加到 3 个实例 | 用户量涨了，随时加容量 |
| **一键回退** | 界面点一下，回到上一个版本/配置 | 升级出问题，快速退回 |
| **一键备份/恢复** | 界面点一下，备份/恢复全部数据 | 数据安全兜底 |

### 2.2 规模选择（三档 + 自定义，部署时选）

| 档位 | 规模 | 形态 | 适用 |
|------|------|------|------|
| **小规模（small）** | 几百人以内 | 单实例 + 垂直扩展 | 起步、试点 |
| **中规模（medium）** | 上千人 | Openfire 集群（2~N 实例）+ 数据库主从 | 正式推广 |
| **大规模（large）** | 上万人/**跨机房** | 多机房集群 + 多 coturn + 数据库跨机房 | 大客户/跨地域容灾 |
| **自定义（custom）** | 按用户方需求 | **自由指定各服务数量**（Openfire N 个 / coturn N 个 / 数据库方案自选） | 客户有明确数量要求 |

> 三档**可平滑升级**：small → medium → large，无需推翻重来。**自定义模式**用于客户对服务数量有明确要求时，自由指定各组件实例数，部署工具按数量动态生成 compose。

### 2.3 工具形态：图形化（Web 控制台）

**不采用命令行**，最终交付一个**完全可视化的部署管理控制台**（浏览器访问，点选操作）。原因：面向测试/部署负责人，图形界面可点可看、不易误操作、能直观看到拓扑和状态。

> **零代码原则**：使用者的任何操作（部署 / 扩展 / 回退 / 备份 / 恢复）都是**界面点一下完成**，绝不要求使用者登录服务器、写命令、改配置。平台底层自动执行 Docker / SQL / 脚本。

### 2.4 高可用要求（容灾/故障切换，全自动）

- 实例/数据库故障**全自动切换**（秒级，无需人工介入）。
- 数据库高可用**不只有「主从」一种方式**，按规模可选多种架构（见第五章）。
- 数据不丢（数据库高可用 + 本地/异地自动备份兜底）。

### 2.5 备份要求（本地 + 异地）

- 备份**不只是本地**，要支持**自动备份到本地 和/或 异地**（可选配置）。
- 定时自动备份 + 手动一键备份，保留多份。

### 2.6 监控平台

- **监控是「完全可视化平台」的核心模块之一**：实时看到所有组件（Openfire 实例 / coturn / 数据库）的运行状态。
- 可视化看板 + 故障自动告警 + 资源趋势预警，并为「何时该扩展」提供依据。

## 三、总体设计（怎么搭）

### 3.1 底座：Docker（不换）

| 演进阶段 | 技术 | 说明 |
|---------|------|------|
| 现在 | docker-compose | 单机，够用 |
| 多机 | docker swarm | compose 文件基本兼容，平滑升级 |
| 超大/多机房 | Kubernetes (k8s) | 上万人/多机房，远期 |

**原则**：前两档都是 Docker 生态，**现有 compose 文件不推翻重写**，只参数化 + 加管理台。

### 3.2 组件解耦（扩谁不动谁）

| 组件 | 作用 | 能否独立扩 | 数据 |
|------|------|-----------|------|
| Openfire | IM 引擎（消息/群聊/通话） | ✅ 集群水平扩 | conf / plugins / fileupload 卷 |
| 数据库（postgres） | 账号/通讯录/归档 | ✅ 多方式高可用 | 数据卷 |
| coturn | 音视频媒体中转 | ✅ 多实例 | 无状态 |

### 3.3 配置驱动（写死 → 参数化）

把现在写死的值全部抽到 `.env`，一份配置控制整套部署：

```
openfire-openfire:5.1.2  →  OPENFIRE_IMAGE=openfire:5.1.2
memory: 1g               →  OPENFIRE_MEMORY=1g
端口 19090/15223/17443    →  OPENFIRE_ADMIN_PORT / C2S_TLS_PORT / WS_PORT
数据库密码                 →  OPENFIRE_DB_PASSWORD=<占位符>
XMPP 域                   →  OPENFIRE_DOMAIN=xmpp.collab.local
```

## 四、规模方案（三档可选）

### 4.1 方案 A：小规模（单实例 + 垂直扩展）

```
用户 ──▶ nginx ──▶ Openfire ×1 ──▶ postgres ×1（+定时备份）
                       └──▶ coturn ×1
```

- 最简单，起步用；扩展方式 = 改 `.env` 加大内存/CPU。

### 4.2 方案 B：中规模（Openfire 集群 + 数据库主从）

```
                 ┌─ Openfire 实例 1
用户 ──▶ nginx ──┼─ Openfire 实例 2   ──▶ postgres 主 ──▶ postgres 从
 （负载均衡）    └─ Openfire 实例 3
  （sticky 会话保持）      （coturn ×1~2）
        ↑ 实例间靠 Hazelcast 插件同步在线状态/会话
```

**三个关键点（大白话）**：

1. **共享一个数据库**：所有实例连同一个 postgres，账号数据只有一份。
2. **Hazelcast 插件**：实例间「互通有无」，知道谁在哪个实例在线，消息才能正确路由（官方插件，适配 Openfire 5.x）。
3. **sticky session（会话粘住）**：BOSH 连接有状态，必须保证**同一个用户一直连同一个实例**（nginx 用 `ip_hash` 或 cookie），不能轮询。

> ⚠️ sticky 是 Openfire 集群最大的坑——不粘住，用户会被「踢」到别的实例导致会话丢失。

### 4.3 方案 C：大规模（跨机房）

```
              机房 A                          机房 B
   ┌────────────────────────┐      ┌────────────────────────┐
   │ Openfire ×N (集群)      │      │ Openfire ×N (集群)      │
   │ coturn ×N              │      │ coturn ×N              │
   │ postgres 集群(高可用)   │◀────▶│ postgres 集群(高可用)   │
   └────────────────────────┘      └────────────────────────┘
              ▲ 跨机房数据库复制 / 备份异地
   ┌──────────────────────────────────────────────┐
   │       全局负载均衡（DNS/GSLB，按地域分流）     │
   └──────────────────────────────────────────────┘
```

- **每个机房** = 一套完整拓扑（Openfire 集群 + coturn + 数据库高可用）。
- **跨机房**：全局负载均衡按地域分机房；数据库跨机房复制（容灾）；备份异地（A 机房数据备到 B 机房）。

## 五、数据库高可用方案（多方式可选，全自动切换）

> 需求定案：数据库高可用**不只有「主从」一种**，按规模可选多种架构，且**故障切换全自动**。

### 5.1 方案分级（按规模选）

| 档位 | 数据库方案 | 故障切换 | 适用 |
|------|-----------|---------|------|
| **单实例 + 备份** | 1 个 postgres + 定时备份 | 手动恢复（RTO 分钟级） | 小规模 |
| **主从流复制** | 1 主 + 1~N 从（读写分离） | 半自动（脚本/工具切换） | 中规模 |
| **Patroni 全自动集群** | 3 节点（主 + 从 + 决策者 etcd） | **全自动秒级切换** | 中大规模（默认推荐） |
| **跨机房复制** | 两机房各一套 Patroni，跨机房复制 | 全自动 + 异地容灾 | 大规模/跨机房 |

### 5.2 Patroni 全自动切换（核心）

- **Patroni**：postgres 的开源高可用管理器，配 **Consul**（分布式协调 + 健康检查 + Web UI）做「仲裁」，主库一挂，**几秒内自动把从库提升为新主**，无需人工。
- 选 **Consul** 而非 etcd 的原因：Consul 内置**健康检查**（服务/节点挂了自动发现）、**服务发现**、**Web UI 可视化**，正好满足「健康状态检查 + 可视化显示」的需求；Patroni 官方同样支持。
- 这也是「全自动」要求的标准解法。

### 5.3 「多数据库」的含义澄清

本方案中「多数据库」指两层，都会覆盖：

1. **多份数据库实例**（高可用冗余）：主从 / Patroni 集群 / 跨机房，是「同一份 Openfire 数据的多个副本」。
2. **多个业务库**（按模块隔离）：整个协作平台不止 Openfire 一个库，还有平台库、监控库等；管理台要能**统一管理多个库**的备份/高可用，不是只盯着 Openfire 库。

## 六、部署管理平台（图形化 Web 控制台）

### 6.1 形态与使用场景

一个独立的 **Web 管理控制台**（浏览器访问），技术栈复用协作平台（前端 Vue3 + 后端 FastAPI）。**跑在实施人员的个人电脑上**，通过远程连接给客户服务器部署/扩展/备份 Openfire。

> 使用场景：实施人员（Openfire 负责人）在自己电脑打开管理台 → 添加「目标服务器」（客户服务器，选一种连接方式）→ 图形化一键部署/扩展/备份 Openfire。管理台不部署在客户服务器上，实施人员全程不写命令、不碰代码、不碰客户 SSH/密码。

### 6.2 功能模块

| 模块 | 界面功能 |
|------|---------|
| **目标服务器** | 添加/管理客户服务器，每台选一种连接方式（Agent / SSH / Docker 远程端口），保存连接凭据 |
| **部署向导** | 选规模（small/medium/large）→ 填参数（端口/密码/域名）→ 点「部署」→ 看进度 → 输出访问地址 |
| **规模管理** | 可视化当前拓扑（几个实例、几个 coturn、数据库状态）→ 点「扩展」选目标实例数 → 自动加实例 |
| **回退管理** | 版本快照历史列表 → 点「回退」→ 一键还原 |
| **备份管理** | 备份列表 + 定时策略配置（本地/异地）+ 点「立即备份」/「恢复」 |
| **监控看板** | 实例健康、在线用户数、资源占用、数据库状态、告警 |

### 6.3 一键操作对应的界面动作

- **一键部署**：部署向导 → 生成 compose → 初始化数据库 → 起容器 + 装插件 → **配置同步（部署参数 ↔ 协作平台配置）→ 自检校验（容器→服务→功能→Bug）**。
- **一键扩展**：装 Hazelcast（首次）→ 起新实例连共享库 → 更新负载均衡 → 健康检查。
- **一键回退**：选快照 → 停当前 → 恢复镜像/配置/数据 → 健康检查。
- **一键备份**：数据库（pg_dump）+ 配置（openfire.xml/security.xml/ofProperty）+ 卷（conf/plugins/fileupload）→ 存本地/异地。
- **一键恢复**：选备份 → 恢复库/配置/卷 → 起容器 → 健康检查。

### 6.4 版本快照机制（回退的基础）

每次「部署/扩展/升级」自动记一个快照（镜像版本 + 配置 + 数据库 schema 版本），形成历史列表，回退 = 选快照一键还原。

### 6.5 连接方式（可插拔，实施人员按客户情况选择）

实施人员在自己电脑上远程管理客户服务器，靠「连接器」打通。管理台支持**三种连接方式**，添加目标服务器时按客户实际情况选一种（不同客户可用不同方式）：

| 连接方式 | 怎么工作 | 需要客户提供 | 适用场景 |
|---------|---------|-------------|---------|
| **Agent 模式（推荐）** | 客户服务器装一个「部署 Agent」，管理台通过 HTTPS 指挥 Agent，Agent 在服务器本机执行 Docker | 一次性装 Agent（可客户自己装，给一键安装包） | 客户不开放 SSH、重视安全 |
| **SSH 直连** | 管理台用 SSH 连客户服务器，远程执行 docker 命令 | SSH 账号/密钥 | 客户愿意提供 SSH 凭据 |
| **Docker 远程端口** | 管理台连客户服务器的 Docker 远程 API（TLS 加密） | 开放 Docker 远程端口 + TLS 证书 | 客户已有 Docker 远程管理能力 |

**后端「连接器」抽象（可插拔）**：后端定义统一接口 `Connector`，三种方式各一个实现（`AgentConnector` / `SSHConnector` / `DockerTlsConnector`），上层的「部署/备份/恢复」逻辑不关心具体连法、只调统一接口。以后加新连接方式（如 Kubernetes）只需新增一个 Connector 实现，不改上层。

> **权限边界说明**：三种方式的权限从大到小 = SSH（可执行任意命令）> Docker 远程端口（Docker 全权）> Agent（只能执行预设操作）。实施人员**默认用 Agent**（权限最小、不碰客户密码）；客户主动给 SSH / 开 Docker 端口时，再选对应方式。

### 6.6 一键部署的「配置同步 + 自检校验」

一键部署不能只部署「空壳 Openfire」，要连同「协作平台对接 Openfire 所必需的配置」一起完成，并逐项校验。部署完成后自动执行两步：

#### ① 配置同步（10 项，逐项校验，名称 + 概要说明）

部署参数 ↔ 协作平台对接配置**双向同步**，每项带「配置名称 + 概要说明 + 状态」：

| # | 配置名称 | 概要说明 | 方向 |
|---|---------|---------|------|
| 1 | `OPENFIRE_XMPP_DOMAIN` | XMPP 域名（账号 JID 后缀），必须与 Openfire 部署域名一致，否则登录失败 | 部署→协作平台 |
| 2 | `OPENFIRE_ADMIN_PASSWORD` | admin 密码，后端调 REST API 认证，必须与部署 admin 密码一致 | 部署→协作平台 |
| 3 | `OPENFIRE_ADMIN_URL` | REST API 地址（同机 openfire:9090 / 远程 IP:端口） | 部署→协作平台 |
| 4 | `OPENFIRE_ADMIN_USERNAME` | REST 认证用户名，固定 admin | 协作平台→部署 |
| 5 | `OPENFIRE_REST_SECRET` | REST API 插件 secret，与 Openfire plugin.restapi.secret 一致 | 协作平台→部署 |
| 6 | coturn 端口 | 前端音视频 ICE 端口，部署的 coturn 必须同端口 | 协作平台→部署 |
| 7 | coturn 静态用户 | 前端 TURN 用户名，coturn 配相同静态用户 | 协作平台→部署 |
| 8 | coturn 静态密码 | 前端 TURN 密码，coturn 配相同静态密码 | 协作平台→部署 |
| 9 | nginx `/http-bind/` | BOSH 反代 → openfire:7070 | 核对 |
| 10 | nginx `/httpfileupload/` | 文件上传反代 → openfire:7070 | 核对 |

#### ② 自检校验（4 层，逐项执行，每项有状态 ✅/❌/⏳）

| 层 | 内容 | 项数 |
|----|------|------|
| L1 容器运行状态 | openfire / openfire-db / coturn 三个容器 Up | 3 |
| L2 Openfire 服务状态 | 管理台 9090、33 张表、5 插件、REST API、admin 认证、域名、/sessions、消息归档 | 8 |
| L3 功能测试 | BOSH 登录、1v1 消息、离线消息、群聊 MUC、音视频、文件上传、MAM、账号同步 | 8 |
| L4 Bug 回归 | 07 缺陷表 46 个 Bug 逐一映射到 L1-L3 检查项 | 汇总 |

> 46 个 Bug 全部映射到检查项；BUG-038（手机端单向呼叫，移动端 Web 固有限制）标「延后」，需原生 App 根治，不阻塞部署。

#### ③ coturn 参数化（写死 → 可配置）

coturn 的端口/用户/密码原来**写死在前端代码里**，改为：**协作平台负责人配置在 `.env`（`COTURN_PORT`/`COTURN_USER`/`COTURN_PASSWORD`），前端经 `/im/credentials` 动态获取（不写死）**。一键部署时读取这些值，让部署的 coturn 照着配，保证音视频中继能通。

## 七、备份与恢复（本地 + 异地）

### 7.1 备份内容（三样）

1. **数据库**：`pg_dump`（账号/通讯录/归档/配置）
2. **配置文件**：openfire.xml、security.xml（密钥）、ofProperty
3. **数据卷**：conf / plugins / fileupload 卷

### 7.2 备份策略

| 策略项 | 设计 |
|--------|------|
| 自动备份 | 每天凌晨定时，保留最近 N 份（N 可配） |
| 手动备份 | 界面「立即备份」 |
| 存储位置 | **本地磁盘** 和/或 **异地**（可选配置：MinIO 对象存储 / 远端 SFTP / 另一机房） |
| 异地规则 | 本地 + 异地双写（本地兜底快、异地容灾） |

### 7.3 异地备份

- 大规模/跨机房场景，备份**自动同步到异地**（另一机房的对象存储/服务器），本机房整机损毁也能从异地恢复。
- **同步工具：`rclone`**（开源，备份同步事实标准，支持 S3/MinIO/阿里 OSS/腾讯 COS/SFTP/FTP/网盘等 50+ 存储）。
- 恢复时可选「从本地恢复」或「从异地恢复」。

## 八、监控平台设计

> 定位：监控是「完全可视化平台」的核心模块——用户实时看到服务状态、故障自动告警、资源不足提前预警，并为「何时扩展」提供依据。

### 8.1 技术栈与归属

监控栈（**Prometheus 采集 + Grafana 可视化 + 各组件 exporter**）随 Openfire **一起部署到目标服务器**的容器内（作为「一键部署」的一部分，与 Openfire/coturn/数据库同栈，跑在客户服务器上）。

> **部署平台的定位（只读展示）**：部署平台本身**不采集、不存储**监控数据——它只通过远程连接器**读取目标服务器上的监控数据**（Prometheus API / 嵌入 Grafana），在「监控看板」页展示。业务数据（Openfire 账号/消息）和监控数据都在目标服务器上，部署平台是「控制台 + 只读展示面板」。

### 8.2 监控对象与指标

| 监控对象 | 关键指标 | 采集方式 |
|---------|---------|---------|
| Openfire 实例（多实例） | 在线用户数、会话数、消息吞吐、BOSH 连接、插件状态 | REST API `/sessions` / JMX / HTTP 探针 |
| coturn | 活跃会话、relay 带宽、CPU/内存 | cadvisor + coturn 指标 |
| 数据库（Patroni 集群） | 连接数、事务、**复制延迟**、主从/主备状态 | postgres-exporter + Patroni REST API |
| 部署管理平台自身 | 健康、任务状态 | 自身暴露 `/health` |

### 8.3 告警设计

| 告警类型 | 触发条件 | 通知方式 |
|---------|---------|---------|
| 实例宕机 | 实例健康探针失败 | 管理台告警面板 + 邮件/IM |
| 资源告警 | CPU/内存/磁盘超阈值（如 80%） | 同上 |
| 数据库告警 | 复制延迟过大 / 主从切换发生 | 同上 |
| 备份失败 | 定时备份任务失败 | 同上 |

### 8.4 与「扩展」「高可用」的联动

1. **监控 → 扩展**：监控数据做容量趋势分析，资源持续走高时，管理台提示「建议扩展」，一键加实例。
2. **监控 → 高可用**：实例/数据库故障被监控捕获 → 触发告警 + 自动切换（见第九章）。
3. **扩展后自动纳入监控**：新加的实例/组件，监控自动发现并开始采集（服务发现）。

### 8.5 随部署一起部署

- 部署 Openfire 时，监控栈（Prometheus + Grafana + exporters）**自动一起部署到目标服务器**（或管理台勾选）。
- 部署平台的「监控看板」页只读目标服务器上的监控数据展示；Grafana 独立看板也跑在目标服务器上（实施人员可单独打开访问）。

## 九、高可用设计（容灾/故障切换）

| 故障场景 | 保障手段 | 切换方式 |
|---------|---------|---------|
| 单个 Openfire 实例挂 | 集群多实例 | 负载均衡自动切到其他实例 |
| 单个 coturn 挂 | 多 coturn | 负载均衡自动剔除故障实例 |
| 数据库主库挂 | Patroni 集群 | **全自动秒级提升从库** |
| 整机挂 | 多机部署（swarm） | 容器在别的机器自动重启 |
| 整机房挂 | 跨机房 + 异地备份 | 全局负载均衡切到另一机房，数据从异地恢复 |

**关键指标**：实例/数据库故障**秒级全自动切换**、数据**零丢失**（高可用 + 双写备份兜底）。

## 十、开发落地计划（软件形态）

| 阶段 | 交付 | 内容 |
|------|------|------|
| P0（MVP） | 阶段 1 标准化 | 参数化 compose + 图形化「部署/备份/恢复」+ **监控看板（复用现有 Prometheus/Grafana）** |
| P1 | 一键扩展 + 回退 | 图形化「扩展/回退」+ 版本快照 + 主从复制 + **资源阈值告警** |
| P2 | 高可用集群 | Hazelcast 集群 + sticky 负载均衡 + Patroni 全自动切换 + **故障自动告警** |
| P3 | 跨机房 | 多机房拓扑 + 跨机房复制 + 异地备份 + **跨机房监控** |

> P0 不动现有部署，只加「参数化 + 管理台」，风险最低，可先验证方向。

## 十一、需求决策记录（已定案）

| # | 问题 | 决策 |
|---|------|------|
| 1 | 部署管理平台部署位置与连接方式 | **跑在实施人员个人电脑上**，远程给客户服务器部署；连接方式**三种可插拔**：Agent 模式（推荐，不碰 SSH/密码）/ SSH 直连 / Docker 远程端口（TLS） |
